## What the plugin does

`run(ctx)` runs once per unit (a sample, or a design arm pooling several samples' cells - the
host runs both axes; `per_unit: "sample"` is declared, matching cellchat/liana/scenic). It only
sums raw counts per (sample, population) among the cells it is handed and writes
`tables/pseudobulk__<population>.csv` (genes x samples) and `tables/pseudobulk_meta.csv`. It never
sees a second arm and fits nothing.

`compare(ctx)` runs once per arm pair, after both arms' `run()` has already written its tables. It
reads both, keeps the populations with at least `min_samples_per_arm` pseudobulk samples in BOTH
arms (the rest go to `tables/deseq2_skipped_populations.csv` with a reason, never silently
dropped), builds the combined counts matrix and colData per population, and hands them to one
`Rscript` invocation that loops over every population: `DESeqDataSetFromMatrix` -> `DESeq` ->
`results(contrast = c("arm", hi, lo))` -> `tables/deseq2_results__<population>.csv`, then draws all
five of DESeq2's own plotting exports through the generated companion: `plotMA`,
`plotDispEsts`, `plotPCA` (on a `vst`), `plotCounts` (of the gene with the smallest `padj`), and
`plotSparsity`.

## MAKER DEFECTS

1. **`scprofile._entry.selftest()` never gives `ctx.r_companion` to the `Context` it builds.**
   `_entry.py:148-169` constructs `Context(None, keys={}, out=d, cores=1, log=log)` with no
   `r_companion=` argument, so it is always `""` - unlike the real run/compare path (`main()` and
   `_compare()`), which both call `_companion_text(plugin_path)` first. Any plugin whose
   `selftest()` wants to exercise its own generated `.draw.R` companion (as the task explicitly
   asks this one to) gets `.draw`/`.figures` undefined if it just uses the `ctx` it was handed for
   an `rscript()` call. **Worked around** in `deseq2.py`'s `selftest()` by reading the sibling
   `kernels/deseq2.draw.R` file directly (the same thing `_companion_text()` does) and passing that
   text into a manually-built `CompareContext(r_companion=...)`, rather than the one the harness
   handed in. I did not edit `_entry.py`. This looks like a `finished_by`-worthy gap in the
   `selftest` mechanism itself - every R-drawing plugin's selftest will hit it the same way - but
   fixing the maker was out of scope for this task ("you may not edit the maker or the host").
2. **`Context.fixture()` unconditionally imports `scanpy`**, even for a plugin that injects only
   `counts` + `label` + `sample` and never asks for `lognorm` (`plugin.py:1124-1150`: it always
   builds and stores a log-normalised layer via `scanpy.pp.normalize_total`/`log1p`). In an
   environment with `anndata`/`numpy`/`pandas`/`matplotlib`/`scipy` but no `scanpy` - exactly the
   venv this task specifies - `ctx.fixture()` raises `ModuleNotFoundError` for *every* plugin's
   selftest, whether or not the plugin's `PLUGIN["inject"]` ever mentions `lognorm`. **Worked
   around** by catching the `ModuleNotFoundError` in `selftest()` and reconstructing exactly the
   counts+label part of the same fixture (identical seed, identical
   `rng.poisson(rng.uniform(0.2, 6.0, ...))` draw) without the unused lognorm step. Not a fix to
   the host; a local substitute for the one piece this plugin actually needs.

Neither defect stopped `run(ctx)`/`compare(ctx)` themselves - both only affect `selftest()`, which
runs in the host's generic harness around a plugin's own function.

## DECISIONS THAT NEEDED A PERSON

- **Pseudobulk rule**: sum raw counts per (sample, population); a `(sample, population)` cell
  below `min_cells` (default 10) is not summed in at all rather than summed with a caveat, matching
  the field's usual practice and `de.py`'s own precedent for the same reason.
- **Design/contrast**: fixed at `~arm`, one factor at two levels, because `compare(ctx)` is handed
  exactly two already-resolved arm directories by the host; no batch or paired term is built. A
  study wanting to control for a technical factor inside one contrast needs a design this plugin
  does not build - named in `upstream.not_used` and `cannot_show`.
- **Reference level**: `ctx.names` gives `(lo, hi)` in declaration order; I read `lo` as the
  reference/control side and `hi` as the side subtracted against it
  (`results(dds, contrast = c("arm", hi, lo))`), matching how `cellchat.draw.R`'s compare script
  treats its own `name_a`/`name_b` ("CellChat's differentials are the SECOND relative to the
  FIRST"). This is a *reading* of an existing convention, not something stated in one place I could
  simply quote - worth a second pair of eyes if it turns out `ctx.names`'s order is not always
  control-first.
- **Threshold defaults**: `alpha=0.05` (not DESeq2's own 0.1) passed identically to both
  `results()` and `plotMA()`, named explicitly in `upstream.defaults_changed` as a deliberate
  deviation. `min_replicates=7` and `fit_type="parametric"` kept at DESeq2's own defaults, exposed
  as config per the project's convention of declaring rather than inheriting silently.
  `max_populations=12` (and each figure family's matching `at_most: 12`) is a new knob this plugin
  invented - there is no upstream precedent for it because DESeq2 itself has no notion of
  "population"; without a cap, a cohort with many populations draws unboundedly, which
  `_check_plan_entry` (validate) would refuse for `items`-based per-population loops. I used a
  manual R `for` loop with a per-figure `file=` expression instead of the plan's `items=`
  mechanism (both are legitimate per `cellchat.draw.R`'s own two patterns), so the `at_most`
  ceiling is enforced by `.at_ceiling()` at draw time rather than by a Python-side `items` list -
  the Python-side `max_populations` cap and the R-side `at_most` are two numbers that must be kept
  equal by hand; I set them to the same value and said so in a comment on both sides, but this is
  exactly the "two numbers kept in step by hand" pattern `PLUGIN_DESIGN.md` warns is fragile.
- **Robustness the tool's own documentation doesn't hand you for free**: `vst()`'s `nsub` failure
  on small gene panels, and the default `sfType="ratio"` size-factor estimator's failure when a
  gene is zero in every sample of a population, were both found by *running* DESeq2 during
  development (not by reading its vignette), and both are handled with a `tryCatch` fallback to
  the alternative DESeq2 itself documents (`varianceStabilizingTransformation`, `sfType =
  "poscounts"`) rather than losing the whole population. Recorded in `upstream.gotchas`.
- **Workflow decision the maker did not absorb**: nothing in `sch dev convert status`'s build
  stages checks that a `per_unit` plugin has declared `report.unit_metrics` - only `validate`
  catches it, after the whole plan stage already reports done. A person has to know to run
  `validate` (which the task's own step 2 says to do, but the `status` output alone would read as
  "build: 8 of 8 complete" with a plugin that `validate` then refuses).
